# План улучшений загрузки фото

## 1. Файл целиком в память (OOM-риск)

**Проблема:** `contentResolver.openInputStream(uri)?.use { it.readBytes() }` загружает весь файл в RAM. Для фото 5–10MB это может вызвать OutOfMemoryError.

**Решение:** Использовать `source().inputStream()` из Okio и потоковую передачу через `RequestBody.create()` без промежуточного буфера в память.

---

## 2. Retrofit создаётся заново для каждого фото

**Проблема:** `Retrofit.Builder().build().create<UploadPhotosApi>()` внутри цикла — лишние аллокации, нет кэширования.

**Решение:** Вынести создание `Retrofit` в DI-модуль как singleton. Переиспользовать `@UploadOkHttpClient`. Для динамического URL использовать `@Url` параметр — `baseUrl` можно оставить фиктивным.

---

## 3. Последовательная загрузка (нет параллелизма)

**Проблема:** Цикл `for (entity in pendingPhotos)` загружает фото по одному. При 10 фото × 3с каждое = 30с ожидания.

**Решение:** Использовать `async/awaitAll` или `coroutineScope { pendingPhotos.map { async { uploadSinglePhoto(it) } } }`. Ограничить параллелизм через `Semaphore(3)` чтобы не перегружать сеть.

---

## 4. Нет retry-механизма

**Проблема:** При ошибке загрузки фото остаётся `PENDING`. Требуется ручной повторный запуск синхронизации.

**Решение:**
- Добавить счётчик попыток в `PhotoEntity` (`retryCount: Int`)
- Реализовать exponential backoff (1с → 2с → 4с → 8с)
- После N неудач переводить в статус `ERROR`
- Опционально: WorkManager для фоновой синхронизации

---

## 5. Нет атомарности при обновлении статуса

**Проблема:** Если приложение упадёт между успешной загрузкой на S3 и `photoDao.completeUpload()`, фото навсегда останется `PENDING`. При повторной синхронизации — дубликат на сервере.

**Решение:**
- Добавить статус `UPLOADING` — выставлять ДО начала загрузки
- При старте приложения проверять `UPLOADING` фото и сбрасывать их в `PENDING` (или удалять если serverUuid уже получен)
- Использовать Room-транзакцию для атомарного обновления

---

## 6. Неиспользуемые статусы в enum

**Проблема:** `PhotoUploadStatusEnum.UPLOADING` и `ERROR` определены, но нигде не выставляются. Мёртвый код.

**Решение:** Либо реализовать их использование (см. пункт 5), либо удалить из enum.

---

## 7. Unsafe cast `result.data as String`

**Проблема:** `result.data as String` — unchecked cast. Если тип изменится, ошибка проявится только в рантайме.

**Решение:** `DomainResult<String>` уже типизирован. Использовать `result.data` напрямую без cast.

---

## 8. Нет валидации файла перед загрузкой

**Проблема:** Не проверяется:
- Существует ли файл по пути
- Доступен ли для чтения
- Не превышает ли `max_file_size` из `UploadUrlResponse`
- Корректный ли `Content-Type`

**Решение:** Добавить валидацию ДО запроса presigned URL. Если файл невалиден — сразу ставить статус `ERROR` с причиной.

---

## 9. Ошибка при получении файла молча игнорируется

**Проблема:** `if (bytes == null) continue` — файл пропускается без логирования, без обновления статуса, без уведомления пользователя.

**Решение:** Логировать ошибку, обновлять статус на `ERROR` с сообщением причины.

---

## 10. Нет прогресса загрузки

**Проблема:** UI показывает только «Отправка...» без прогресса. Пользователь не знает, сколько фото обработано и сколько осталось.

**Решение:**
- Добавить `Flow<SyncProgress>` в `IPhotoRepository` (processed / total)
- Emit-ить прогресс после каждого фото
- Отображать в UI: «Загружено 3 из 10»

---

## Приоритизация

| # | Приоритет | Усилие | Описание |
|---|-----------|--------|----------|
| 1 | **Критично** | Низкое | Unsafe cast, молчаливый skip файлов |
| 2 | **Высокий** | Среднее | Потоковая загрузка (OOM), атомарность статуса |
| 3 | **Средний** | Среднее | Retry с backoff, прогресс загрузки |
| 4 | **Низкий** | Низкое | Параллелизм, валидация, очистка enum |
| 5 | **Низкий** | Среднее | WorkManager для фоновой синхронизации |
